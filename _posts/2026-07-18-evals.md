I would like to suggest an Evals feature and share a few observations based on my experience building agents.

While building an agent, evaluating its responses before deploying it to production is very important. However, I feel evaluation is equally valuable after the agent is deployed. As the agent interacts with real users, Evals could help identify recurring issues, monitor performance over time, and ensure that updates to prompts, tools, or guardrails continue to produce high-quality responses.

At the moment, I usually test the agent manually by trying different prompts, reviewing the responses, and making adjustments to the instructions, tool parameters, and guardrails. Even after deployment, understanding how the agent performs often involves manually reviewing conversations and user feedback. This process is quite repetitive and can take a considerable amount of time.

I was wondering if an Agent Evals feature could help make this process easier.

The idea behind Evals is to evaluate an agent's responses using different evaluation methods and provide an overall view of where the agent performs well and where it could be improved throughout its lifecycle.

1. Feedback Evals

For example, if I build a support agent, it would be useful to collect feedback directly from users.

Traditionally, chatbot assistants have used a thumbs-up/thumbs-down feedback mechanism. I think a similar approach could work well here, with a bit more structure for agent evaluation.

Each response could have a feedback option (such as a thumbs-down button). When selected, users could choose one or more reasons from a list, such as:

- Incorrect tool used
- Inaccurate response
- Incorrect references
- Hallucinated information
- Incomplete answer
- Other

Each category could also be assigned a severity score (for example, 1 to 5). Over time, this could provide a clear picture of the areas where the agent is struggling and help prioritize improvements based on real user feedback.

Having this aggregated across evaluation runs would make it easier to identify recurring issues instead of reviewing conversations one by one.

2. LLM as a Judge

Another evaluation method could be LLM as a Judge.

The agent's responses could be anonymized and evaluated by a stronger flagship LLM against a predefined rubric such as:

- Accuracy
- Completeness
- Relevance
- Tool usage
- Instruction following
- Groundedness

Anonymizing the responses before evaluation could help reduce model-specific bias and make the evaluation more objective.

3. Automated Evals

It would also be useful if developers could create their own evaluation metrics.

For example, they could define:

- A user query
- An expected response or expected behavior
- A custom scoring rubric

Instead of requiring an exact text match, the evaluation could compare the semantic similarity between the expected and actual responses. This would make it easier to build regression tests and verify that changes to prompts, tools, or guardrails have not negatively affected the agent's quality.

Another possibility could be supporting automated evaluation of tool execution. For example, validating whether the correct tool was invoked, whether the expected sequence of tools was followed, whether the required parameters were passed correctly, or whether the agent should have used a tool but instead responded directly. This could be especially useful for workflow-oriented agents.

4. Agentic Evals

Additionally, it would be interesting if there were an agentic element while creating Evals.

Based on the evaluation results, the system could intelligently analyze the agent's performance and provide actionable suggestions. For example, it could:

- Suggest improvements to prompts or instructions.
- Recommend changes to tool configurations or guardrails.
- Highlight recurring failure patterns.
- Suggest additional evaluation metrics based on observed failures.
- Recommend new test cases that cover edge cases the agent is currently missing.

This could make the evaluation process much more efficient, especially when iterating on an agent.

Overall, I feel a feature like this could significantly reduce manual testing effort, provide better visibility into agent performance, and help developers continuously improve their agents both before and after deployment.

These are just a few ideas based on my experience while building agents. If something similar is already planned or already being explored, I'd be excited to see it. I would love to hear everyone's thoughts.
